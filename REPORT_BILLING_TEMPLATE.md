## 1. Implementation summary

A vendor uploads one clean invoice PDF. FlashFoods stores it privately, renders
it with PDF.js for one-time field placement, and then draws Roboto text and item
rows onto a copy of that exact PDF at invoice time. The vendor's logo, images,
colours, borders, backgrounds, static text and layout are preserved; nothing is
rebuilt in HTML/CSS, no design editor exists, and no white-box masking is done.

Invoices are issued only for orders that are `completed`, have `collectedAt`,
carry payment evidence, have a positive persisted payable, and belong to a shop
with an active configured template. Issuance is idempotent, numbered atomically
per shop, and frozen into an immutable snapshot plus a stored PDF.

Shops without an active template — never uploaded, uploaded-but-unconfigured,
configured-but-not-activated, or removed — keep the existing FlashFoods default
order bill on `/orders/:id`. No generic FlashFoods PDF is ever generated, and the
download action renders only when an `Invoice` document actually exists.

## 3. Database schema and indexes

`InvoiceTemplate` — one document per shop (`shop` unique). Embedded `versions[]`
each with `version`, `originalFileKey`, `originalFileName`, `byteSize`, `sha256`,
`pageCount`, `pageSizes[]`, `mapping` (Mixed, PDF-native coordinates),
`mappingHash`, `previewMappingHash`, `previewedAt`, `status`
(`uploaded|configured|previewed|active|superseded`), timestamps; plus
`currentVersionId`, `nextVersion`. No index beyond the unique `shop`.

`Invoice` — `order` (unique), `shop`, `customer`, `number` (unique), `snapshot`
(Mixed), `templateVersionId`, `templateSha256`, `mappingHash`,
`rendererVersion`, `storageKey`, `outputSha256`, `byteSize`, `pageCount`,
`issuedAt`, `events[]`. Indexes: unique `order`, unique `number`,
`{shop, issuedAt:-1}`, `{customer, issuedAt:-1}`. Mongoose hooks reject any
non-insert save and any update touching a protected path, so an issued invoice
cannot be rewritten.

`InvoiceCounter` — `shop` (unique), `seq`; allocation is a single
`findOneAndUpdate({shop}, {$inc:{seq:1}}, {upsert:true})`.

## 4. PDF storage architecture

`utils/invoice/storage.js`, root `BILLING_STORAGE_DIR` (default `./storage`,
git-ignored, never inside `public/`):

- `templates/<shop>/<template>/v<n>-<sha256>.pdf` — uploaded master, written once.
- `invoices/<shop>/<invoiceId>/<sha256>.pdf` — generated output.
- `previews/<shop>/<template>/v<n>-<mappingHash>.pdf` — sample previews.

Writes are atomic (`tmp` + rename) with a resolved-path prefix check that rejects
traversal. Reads happen only inside authorized vendor/student routes; nothing is
statically served. No Cloudinary path was used or assumed for documents.

## 5. Roboto integration and glyph verification

`assets/fonts/Roboto/` holds real Roboto Regular/Medium/Bold TTFs plus the
Apache-2.0 licence and `NOTICE.md`. The generator registers `@pdf-lib/fontkit`
and embeds the three files once per `PDFDocument` with `subset: false`. Unit
tests assert every file parses and contains the `₹` (U+20B9) glyph; the visual
checks below show `₹120.00`, `₹355.00`, `₹339.50` rendered in the output.
No vendor font upload exists and no standard-14 font is used for dynamic text.

## 6. Template mapping and coordinate conversion

The browser converts clicks through `viewport.convertToPdfPoint` after
normalizing CSS pixels to viewport units, so page size, scale and rotation are
handled by PDF.js. Only PDF user-space coordinates are stored (3-decimal
rounding): per-field `x`, `y` (baseline), `align`, `fontSize`, `font`,
`maxWidth`, `maxLines`, `lineHeight`, `truncate`; per-table `originX/originY`,
`rowHeight`, `maxRowsFirstPage`, `baselineOffsetFromRowTop`, `columns[]` and
`continuation`. `x` is the left edge (left), centre (center) or right edge
(right) anchor; the renderer measures text to keep the anchor fixed.

Validation (`utils/invoice/mapping.js`) rejects NaN/negative/out-of-page
geometry, unsupported sizes/alignments/fonts, missing required fields, missing
item-table columns, invalid tax mode and out-of-range values; the canonical JSON
hash is stable. Activation freezes the mapping; a replacement PDF creates a new
version with an empty mapping.

## 7. Invoice numbering mechanism

`INV-<shop-slug>-<000001>` (current documented placeholder; DECISION-1 open).
Numbers come from the shop-scoped counter `$inc`; they are never derived from
counts. The number is allocated before rendering and only on the issuance path,
so an ineligible order consumes nothing. Duplicate-key races resolve to the
winning invoice, so a number can never be issued twice.

## 8. Payment eligibility and generation trigger

`evaluateEligibility` requires `status === "completed"`, `collectedAt`, payment
evidence (`amountChargedPaise > 0`, or `paymentNote === "mock"` from the real
mock-checkout gate), and `toPaise(order.total) > 0`; it also requires an active
version with a mapping. Status alone never proves capture.

Both completion paths (`POST /vendor/verify` OTP and `POST /vendor/verify-qr`
QR) call `issueInvoiceBestEffort(order._id)` after the atomic completion. It is
wrapped in try/catch, logs the reason when issuance is skipped, and never
changes the response, flash, redirect or handover JSON. The download routes call
`ensureInvoiceForOrder` as the lazy path for historical eligible orders. No bulk
backfill exists.

## 9. Snapshot, idempotency and immutability

`ensureInvoiceForOrder` returns an existing invoice before doing any work;
generation is then render → store output → create invoice, with a unique `order`
index as the final arbiter (duplicate key returns the stored winner). The
snapshot contains the full data contract, template version id/version/sha256/
mapping hash/page, renderer version, eligibility source and time, output sha256,
byte size and page count, canonical-hashed and deep-frozen. An invoice keeps its
own PDF bytes, so replacing or removing a template never changes it, and
refund/adjustment events are appended only to `events`.

## 19. Addendum — field-fitting correction (2026-10-30)

### Reported symptom

`Save + sample invoice` always failed with "A value is too long for its field.
Increase its width or lines.", even after the vendor widened Amount in Words.

### Root cause (measured, not assumed)

`node scripts/diagnose-invoice-fields.mjs` measures every configured field with
the bundled Roboto metrics against the real sample dataset and a clean master:

| Scenario | Field | Max width | Max lines | Required | Result |
|---|---|---:|---:|---:|---|
| Editor defaults | all 8 fields | ≥140 | as configured | 1 | render OK |
| Mapping saved by the pre-fix editor | `invoiceNumber` (`SAMPLE`, 39.1 pt @10 pt bold) | 24 | 1 | 2 | **text_overflow** |
| Mapping saved by the pre-fix editor | `total` (`₹339.50`, 44.2 pt @12 pt) | 24 | 1 | 3 | **text_overflow** |
| Amount in Words placed with the panel defaults | `amountInWords` (218.2 pt @9 pt) | 180 | 1 | 2 | **text_overflow** |
| Long name/number in roomy boxes | all | ≥140 | 1–2 | 1 | render OK |

Two defects combined: right-margin fields stored a 24 pt box (the old
`pageWidth - x - 24` math) that can never print a value, and the renderer threw
for whichever field was too small without naming it — so widening Amount in
Words could not fix, or even reveal, the actual failing field. Amount in Words
was not the failing field in the reported configuration.

### Fix

- **Diagnostics:** `layoutText` now reports `field` (or `column`), `fontSize`,
  `maxWidth`, `maxLines`, `requiredLines`, measured `textWidth`, `longestWordWidth`
  and `canWrap`; no customer, payment or value text is included. The vendor sees
  e.g. `Amount in words: this value needs 2 lines at 9 pt, but only 1 line is
  configured. Increase Max lines or Max width.` The affected row is highlighted
  (`li.is-error`) and its settings load into the panel.
- **Geometry:** `availableRoom()` bounds every field box by the space on its
  anchor side (right-aligned text grows leftwards), so stored widths can no
  longer describe a box that leaves the page.
- **Editor:** placed fields are selectable and editable in place (Max width, Max
  lines, font size, alignment apply to the selected field); placement keeps the
  loaded settings instead of resetting to panel defaults; boxes narrower than
  four characters are widened on load with a visible notice naming them, so an
  old broken mapping can be saved and previewed again; the selected field's
  configured box is drawn over the PDF.
- **Row fit:** column lines are capped to `floor(rowHeight / (fontSize × 1.2))` at
  save and render time (this fixed 2-line descriptions printing over the next
  row), the default row height is 22 pt, and changing Row height re-derives the
  budgets.

No truncation was added for money fields, no font size is shrunk automatically,
and no validation was bypassed: an impossible box still fails, now with the
field name and measurements.

## F13 — Production invoice issuance and retrieval (2026-10-31)

**Status: code-level causes fixed and verified locally. The production root
cause is NOT yet proven — this environment had no access to the `flashfoods.in`
database, its storage volume or its logs, and no failing order ID was supplied.**
Nothing was deployed, and no production record, template or file was touched.
`scripts/diagnose-production-billing.mjs` is the read-only step that must run
against production before Phase 4/5 actions are taken.

### The two production errors, and what each one actually means

| Symptom | Emitted by | Meaning |
|---|---|---|
| `This canteen has not enabled custom invoices.` | `ensureInvoiceForOrder()` → `no_active_template` | Either no `InvoiceTemplate` for **that** shop in **that** database, a dangling `currentVersionId`, a non-active version, or (previously) a mapping/PDF problem the resolver could not name |
| `The invoice file could not be read.` | `GET /orders/:id/invoice` → `getFile()` threw | An `Invoice` row exists but its PDF is missing/unreadable **from the storage path this process sees** |

The second error is only reachable when an invoice record already exists, so
these are genuinely independent failures. The old code could not distinguish
"no template configured" from "template configured but unusable", and returned
existing invoices without checking that their PDFs still existed.

### Fixes (all local, all additive)

1. **One definition of a usable template.** `resolveActiveTemplate()` in
   `utils/invoice/invoice-resolver.js` now evaluates every condition explicitly
   (record → shop match → current version → `status === "active"` → mapping
   present → mapping validates → original PDF readable → optional SHA-256 match)
   and returns a named reason. `findActiveVersion()` delegates to it, so the
   resolver's answer is unchanged for existing callers.
2. **The vendor UI can no longer promise what the resolver refuses.**
   `getBillingCardState()` and the billing-template page use the same function;
   a version that is flagged active but unusable is reported as
   `unusable — <reason>` instead of `Active vN`.
3. **Issued invoices are immutable *and* verified.** When an `Invoice` row
   exists, its stored PDF is now verified (existence → byte size → `%PDF-`
   signature → SHA-256 against `outputSha256`) before it is served. On failure
   the resolver returns `invoice_file_missing` with the exact sub-code; it never
   allocates a new number, never re-renders, never re-templates. On success the
   verified bytes are returned directly, so a download reads the file once.
4. **View vs Download.** `GET /orders/:id/invoice` serves `inline` by default
   and `attachment` for `?download=1`, both from the identical bytes. The order
   page shows a "Your Invoice" card with `View Invoice` and `Download PDF`.
5. **Diagnosable failures.** Broad `catch {}` blocks were replaced with a
   structured, PII-free `[billing] invoice delivery failed` record (correlation
   ID, order ID, invoice ID, reason, storage error code, size/signature/checksum
   flags) plus an `X-Correlation-Id` response header. Student-facing messages
   stay short and safe.
6. **Explicit environment configuration.** `config/db.js` reports which URI
   variable was selected and warns when both are set and differ; in production it
   refuses to fall back to a localhost database. `server.js` warns when
   `BILLING_STORAGE_DIR` is unset, because a relative `./storage` path is
   ephemeral on hosted platforms and not shared between instances.

## F15 — Billing Template Reset / Cleanup (2026-10-31)

Scope: a destructive **Reset Template** action beside **Upload PDF** in
`views/partials/menu-manager.ejs`, a shop-scoped
`POST /vendor/menu/billing-template/reset`, and one reset service that removes
the editable configuration without ever touching issued invoices.

### Reset dependency map (audited before implementation)

| Artefact | Stored where | Referenced by | Reset behaviour |
|---|---|---|---|
| `InvoiceTemplate` document | `invoicetemplates` (unique per `shop`) | vendor dashboard, resolver | pointer cleared + mappings dropped; record deleted when no revision is referenced |
| Template revision record (`versions[]`) | same document | `Invoice.templateVersionId` (string) | removed when unreferenced; `status:"archived"` when referenced |
| Original uploaded PDF | `templates/<shop>/<templateId>/v<n>-<sha256>.pdf` | revision record | deleted when unreferenced; **kept** when referenced |
| Sample / preview PDF | `previews/<shop>/<templateId>/v<n>-<mappingHash>.pdf` | nothing (derived) | always deleted |
| Generated invoice PDF | `invoices/<shop>/<invoiceId>/<sha256>.pdf` | `Invoice.storageKey` | never touched |
| `Invoice` document (number, snapshot, totals) | `invoices` | student/vendor download | never touched (immutable model) |
| `InvoiceCounter` sequence | `invoicecounters` | `allocateInvoiceNumber` | never touched |
| Order + default order bill (`views/orders/show.ejs`) | `orders` / view | student order page | never touched |

Storage cleanup derives paths from the shop's own template id only
(`templates/<shopId>/<templateId>`, `previews/<shopId>/<templateId>`). The sweep
walks inside the resolved directory and refuses any key outside
`BILLING_STORAGE_DIR`; `invoices/` is never a target.

### Operation order (safe and idempotent)

1. Load the template for `req.vendorShopId` only — no shop id is read from the body.
2. `Invoice.distinct("templateVersionId", { shop, $in: [all revision ids] })`
   partitions revisions into archived (referenced) and removable.
3. One atomic single-document write: `currentVersionId = null`, mapping / hash /
   preview state cleared, referenced revisions set to `status:"archived"`
   (original PDF, sha and provenance kept), unreferenced revisions removed.
4. Sweep the template directory (keeping archived `originalFileKey`s) and then
   the preview directory.
5. Delete the now-empty record **last**, and only when cleanup reported no error,
   so a failed sweep can always be retried by repeating the reset.
6. A database failure in step 3 returns `reset_failed` before any file is
   deleted, so the template stays fully usable.

Every step is repeatable: a second reset finds an archived-only or removed state
and changes nothing.

### Evidence from the E2E run

`[billing] template reset shop=… archived=1 removed=1 preservedFiles=1 deletedFiles=2`

- archived 1 revision: the one referenced by the issued invoice (original PDF kept).
- removed 1 revision: the unreferenced replacement upload (record + PDF deleted).
- deleted 2 files: that unreferenced source PDF and the derived sample preview.
- The historical invoice returned identical bytes (`sha256` unchanged) after reset.
- Numbering continued (`…000002` in the unit test after a reset).
