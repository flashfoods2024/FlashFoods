# 05 — Invoice Data and Generation (PROPOSED)

Defines the invoice data contract, its mapping from persisted documents, the
reconciliation rules, payment eligibility, numbering, idempotency, snapshots and
refund/adjustment treatment.

Locked rules: `00_PRODUCT_CONTRACT.md` §§7–9. Existing fields and money
utilities: `01_CODEBASE_AUDIT.md` §§2, 7, 8. Rendering: `04_PDF_TEMPLATE_ENGINE.md`.

---

## 1. Invoice data contract (frozen shape)

`invoice-data.js` returns this plain object. It is the only input to the
renderer and the only content of the snapshot. It contains **no Mongoose
documents, no getters, no lazy references**.

```json
{

  "issuedAt": "2026-10-30T14:05:11.000Z",
  "invoice": {

    "dateIst": "30/10/2026",
```

Rules:

- Every `*Paise` value is an integer. Every `*Text` value is generated by one
  shared formatter using `en-IN` grouping with 2 decimals and `₹`.
- `mode` is `"final"` for real invoices and `"sample"` for previews. Sample mode
  uses synthetic values and `invoice.number = "SAMPLE"`.
- All dates are rendered in **Asia/Kolkata**, matching the existing order views
  (`toLocaleString("en-IN", { timeZone: "Asia/Kolkata" })`).
- Extra fields may be added for new mapped fields, but existing names are
  stable. `schemaVersion` increments on breaking changes.

## 2. Mapping from actual `Order` fields

| Contract field | Persisted source | Rule |
|---|---|---|
| `order.id` | `order._id` | String |
| `order.shortRef` | `String(order._id).slice(-6).toUpperCase()` | Matches existing UI convention (`orderNumber` in pickup handover) |
| `order.createdAtIst` | `order.createdAt` | IST format |
| `order.collectedAtIst` | `order.collectedAt` | IST; required for eligibility |
| `order.pickupMethod` | `order.pickupMethod` (`qr`/`otp`) | Display level only |
| `order.pickupTimeIst` | `order.pickupTime` | Empty when null |
| `order.status` | `order.status` | Must be `completed` |
| `shop.*` | `Shop` document (`name`, `slug`, `_id`) | Loaded fresh at generation; seller constants come from template config, not invented |
| `customer.name/phone/email` | `User` document (`name`, `phone`, `email`) | Only these exist; do not invent address/GSTIN |
| `lines[]` | `order.items` where `status !== "removed"` | Unit price is `item.price` (already variant-aware at order time) |
| `lines[].description` | `item.name` + `" (" + item.variantName + ")"` when `variantName` | Matches precedent in `views/orders/show.ejs` display of variant |
| `lines[].quantity` | `item.quantity` | Integer ≥ 1 |
| `totals.foodSubtotalPaise` | Sum of `toPaise(item.price) * item.quantity` over billable lines | Integer paise; **no** re-pricing from `MenuItem` |
| `totals.discountPercent` | `order.discountPercent` | Persisted snapshot of the discount at order time |
| `totals.discountPaise` | `order.discountAmountPaise` when > 0, else `computeDiscountPaise(foodSubtotalPaise, discountPercent)` | Use the persisted value first; the utility is the fallback for legacy orders |
| `totals.parcelChargePaise` | `toPaise(order.parcelCharge)` when `orderType === "parcel"` | Never derived from the current shop settings |
| `totals.payablePaise` | `toPaise(order.total)` | Post-adjustment authoritative payable |
| `payment.*` | `order.paymentNote`, `transactionId`, `razorpayPaymentId`, `gatewayTxnId`, `amountChargedPaise`, `refundStatus`, `refundId`, `refundProcessedAt` | Display only |
| `adjustment.*` | `order.adjustedAt`, `adjustmentReason`, removed `items`, `originalTotal`, `updatedTotal`, `refundAmount` | See §9 |

**Forbidden sources:** request body, query string, session cart, live
`MenuItem` prices, live `Shop.parcelCharge`/`Shop.discount`, recalculated totals
from anything other than persisted order data.

**Important subtlety:** `order.total` changes when an adjustment occurs
(`adjustOrderPaid` writes `total = updatedTotal`), while `amountChargedPaise`
keeps the originally captured amount and `refundAmount` records the difference.
The invoice must bill `order.total` (payable now) and present the refund as
metadata — never re-add removed items, never bill the original total as the
amount due.

## 3. Shop / business information

Available from `Shop`: `name`, `slug`. **Not available:** address, GSTIN, phone,
email, legal entity name, bank details, terms.

Rules:

- Only `shop.name` (and the vendor's own printed design) identifies the seller.
- Any other seller detail must come from **vendor-configured constant text**
  (`constants.sellerNote`, `constants.termsText`) stored with the template
  version and typed by the vendor — it is their own invoice content, not
  FlashFoods data. Constants are limited to 2 short text blocks (max 300 chars
  each), rendered in Roboto.
- If a statutory field is legally required and not configured, the invoice is
  incomplete by design of the vendor's template, not by a FlashFoods bug. Record
  it in DECISION-6. Do **not** fabricate a GSTIN or address.
- Do not print FlashFoods contact details as the seller.

---

## 4. Customer information

Available from `User` (populated at generation): `name`, `phone`, `email`.

Rules:

- `name` is required (User schema requires it).
- `phone` may be empty string; render the mapped field as blank rather than
  printing "undefined"/"null".
- `email` may be present; showing it is optional (vendor maps the field or not).
- No billing address, no delivery address, no GSTIN is available. If the vendor
  maps a customer-detail area expecting address, the renderer prints the
  configured label plus available values only.
- Personal data: the invoice contains the student's name/phone/email. It is
  served only to the owning student and to the shop's vendor. Do not log full
  customer objects in error paths.

## 5. Item, variant, discount, parcel and tax rules

### 5.1 Items

- Only `status !== "removed"` lines are billable.
- `item.price` is the unit price recorded at order time (variant price when a
  variant was chosen, because `buildOrderItemsFromCart` stores the resolved
  variant price in `price`).
- `variantName` is displayed with the item name; `variantId`/`variantPrice` are
  not printed separately unless a vendor maps an extra column.
- Quantities are the persisted integers; never recomputed from the cart.
- A line with non-finite `price` or non-integer/≤0 `quantity` fails the build
  (`reason: "invalid_order_item"`) — do not guess.

### 5.2 Discount

- Persisted percent + amount; food subtotal only.
- Display as a negative line labeled with the percent (`Discount (10%)`).
- If `discountPercent` is 0 and `discountAmountPaise` is 0, the mapped discount
  field is left blank (not `₹0.00`), unless the vendor chose `showZeroDiscount`.

### 5.3 Parcel charge

- Only when `orderType === "parcel"` and `parcelCharge > 0`.
- Otherwise the mapped parcel field is blank.
- Never read `Shop.parcelChargeEnabled` or `Shop.parcelCharge` for an existing
  order: they may have changed since the order was placed (the existing code
  also states "Historical orders are unaffected").

### 5.4 Tax configuration (conservative, no invention)

Because no tax data exists (verified), tax is **opt-in and display-only**:

- `taxMode: "none"` (default): CGST/SGST fields are blank; no tax is computed.
- `taxMode: "inclusive_breakdown"` (vendor-enabled with declared rates):
  - The persisted `order.total` is treated as the **tax-inclusive payable**
    amount. The invoice does not add tax.
  - `taxableBasePaise = round(payablePaise * 10000 / (10000 + cgstBasisPoints + sgstBasisPoints))`
    where rates are stored as basis points (for example 2.5% = 250).
  - `cgstPaise = round(taxableBasePaise * cgstBasisPoints / 10000)`;
    `sgstPaise = round(taxableBasePaise * sgstBasisPoints / 10000)`.
  - Reconciliation: `taxableBasePaise + cgstPaise + sgstPaise` must equal
    `payablePaise`. If rounding does not reconcile, adjust the taxable base by
    the remainder in a single deterministic step (documented in code and
    tested), or fail with `reason: "tax_reconciliation_failed"`. Choose one and
    test it; do not silently produce a total that differs by a paisa.
  - The CGST/SGST lines are additional breakdown rows; `payablePaise` remains the
    single amount due.
- `taxMode: "exclusive_add"` is **forbidden**: it would change the amount
  payable and break reconciliation with `amountChargedPaise`.
- Rates and mode are vendor configuration stored on the template version, not
  inferred. If a vendor asks for tax and the mode is ambiguous, stop for
  DECISION-2.

## 6. Totals and reconciliation

The invoice generation step must pass all of these before rendering:

```text
let food = Σ toPaise(item.price) * item.quantity        // billable lines only
let discount = persisted discountPaise (fallback computeDiscountPaise(food, pct))
let parcel = orderType === "parcel" ? toPaise(order.parcelCharge) : 0
let payable = toPaise(order.total)

assert food, discount, parcel, payable are finite integers
assert 0 <= discount <= food
assert payable > 0
assert food - discount + parcel === payable
```

Tolerance policy: **exact equality in integer paise**. No ±1 tolerance. If a
legacy order fails, the builder fails with `reason: "totals_mismatch"` and
records the components; it must not "fix" the total by altering the persisted
value or by writing a different number on the invoice. Legacy failures are
reported in the final report as reconciliation exceptions, not silently
invoiced.

Note: `order.total` uses `fromPaise(totalPaise)` (a single rounding at the
boundary), so `toPaise(order.total)` returns the original integer for all
amounts produced by the current code. Verify this with a fixture.

Secondary assertion when the order was adjusted:

```text
if (order.adjustedAt) {
  assert Number.isFinite(toPaise(order.refundAmount))
  assert payable + toPaise(order.refundAmount) === amountChargedPaise
}
```

If this fails, record it but still allow the invoice **only** when the primary
reconciliation passes and `refundStatus` is known; the mismatch is reported.

## 7. Payment eligibility

Decision function (single source of truth in `invoice-resolver.js`):

```text
eligible(order):
  1. order.status === "completed"                    else reason "not_completed"
  2. order.collectedAt != null                       else reason "not_collected"
  3. capturedEvidence(order)                         else reason "payment_not_verified"
  4. toPaise(order.total) finite && > 0              else reason "invalid_payable"
  5. invoice already exists?                         → return existing (idempotent)
  6. active template version for order.shop?         else reason "no_active_template"
  7. totals reconcile (§6)                           else reason "totals_mismatch"
```

`capturedEvidence(order)`:

```text
if (Number.isFinite(Number(order.amountChargedPaise)) && Number(order.amountChargedPaise) > 0)
    return true;                       // Razorpay verify, PhonePe verify, Easebuzz, webhook, mock
if (order.paymentNote === "mock")      return true;   // defensive: mock path always sets both
return false;
```

Per-path evidence (verified in `01_CODEBASE_AUDIT.md` §7):

| Path | Evidence | Invoice eligibility |
|---|---|---|
| Razorpay `/verify-payment` | gateway `captured` + exact amount match, `amountChargedPaise` = gateway amount | Eligible |
| Razorpay webhook `payment.captured` | valid signature; `amountChargedPaise = toPaise(order.total)` (derived, not compared to gateway amount) | Eligible — but record the weaker evidence in the snapshot (`payment.verificationSource`) |
| Easebuzz callback | hash-verified response; `amountChargedPaise = toPaise(order.total)`; amount verification outstanding per existing code comment | Eligible — record `verificationSource: "easebuzz_hash"` and list DECISION-7 |
| PhonePe callback | `verifyPhonePeCompletedPayment` amount match | Eligible |
| Mock `/orders/checkout` | only `testing` shop; `paymentNote: "mock"`; `amountChargedPaise` written | Eligible — snapshot must mark `mock: true` |
| Any `pending_payment` / `cancelled` | — | Ineligible |

Add `payment.verificationSource` to the snapshot (`razorpay_amount_verified`,
`razorpay_webhook`, `easebuzz_hash`, `phonepe_amount_verified`, `mock`) so the
invoice's evidentiary basis is auditable. This is metadata only; it does not
change the PDF.

Do **not** treat `status === "completed"` alone as proof of capture. Do not
query the gateway at invoice time (no live calls, per `.ai/test.md` and to keep
generation offline-safe).

### 7.1 Default-billing fallback (locked)

The existing FlashFoods order detail UI (`views/orders/show.ejs`) is both the
default billing experience and the fallback for this feature.

- **No active custom template** (never uploaded, uploaded-but-unconfigured, or
  removed) → no invoice is generated, no `Invoice` document exists, no number is
  allocated, no invoice download action is shown, and the student sees the
  existing default order bill exactly as today. `no_active_template` is a normal
  state, not an error and not a missing experience.
- **Active template, order not yet collected** → no invoice yet; the default
  bill with normal tracking is shown.
- **Active template, eligible `completed` order** → issue the custom PDF overlay
  invoice once and offer its download alongside the existing order-detail
  content.
- **No generic FlashFoods PDF invoice or receipt is produced in any case.** The
  fallback is the HTML order-detail bill, not a PDF.
- **No bulk backfill:** completed orders from before activation are invoiced only
  if resolved on demand after activation, once, under the same §7 rules.

Eligibility is unchanged: a custom PDF still requires `completed` +
`collectedAt` + payment evidence + an active template with a complete mapping.

## 8. Completion trigger and idempotency

### 8.1 Trigger points

Verified completion paths: `POST /vendor/verify` (OTP) and
`POST /vendor/verify-qr` (QR). Re-verify before coding, including admin flows
(none found).

Integration shape (PROPOSED):

```text
// after the atomic findOneAndUpdate that returns the completed order
// (and after the existing notification/flash work)
queueInvoiceIssue(order._id)   // best-effort, never awaited in a way that can
                               // fail the pickup response
```

Requirements:

- The pickup response, flash message, redirect and JSON handover must be
  byte-for-byte unchanged.
- Invoice work must be wrapped in `try/catch`; a failure logs and is ignored by
  the pickup request.
- Do not create a new status, do not delay completion, do not gate the response
  on rendering.
- Lazy ensure on download covers a missed background attempt.
- If a background job/queue already exists in the repo, use it; if not, do not
  add a queue dependency for this feature. A fire-and-forget promise plus lazy
  ensure is sufficient. (VERIFY-AT-BUILD: confirm no queue exists.)

### 8.2 Idempotency

Three independent layers:

1. **Read-before-write**: `Invoice.findOne({ order: orderId })` → return it.
2. **Unique index**: `{ order: 1 }` unique on `Invoice`. A racing insert throws
   `E11000`; catch it, re-read and return the winner. Never surface the error.
3. **Immutable file key**: generated file key = `invoices/<shopId>/<invoiceId>/<sha256>.pdf`.
   A duplicate write is a no-op/identical file.

Generation must be safe to call from multiple routes, multiple times, and
concurrently. A test must prove: 10 parallel `ensureInvoiceForOrder(orderId)`
calls produce exactly one `Invoice`, one number, one file.

### 8.3 Failure handling

```text
if render fails → no Invoice document (or a FAILED attempt record), no file,
                   no number consumed if numbering is allocated last
```

Ordering rule: allocate the invoice number **after** snapshot build and
**before** the insert, but only after a successful render into memory. Then:

- If the insert fails for a non-duplicate reason, the number is burned (gap).
  That is acceptable and must be documented as a gap-tolerant sequence. Never
  reuse a burned number.
- If the render fails, no number is allocated at all.
- A failed attempt is logged with `orderId`, `reason`, `templateVersionId`,
  timestamp — never with customer PII beyond the order id.

## 9. Invoice number generation

PROPOSED, atomic, shop-scoped:

```js
// models/InvoiceCounter.js
{ shop: ObjectId (unique), seq: Number, updatedAt: Date }

// utils/invoice/invoice-number.js
const counter = await InvoiceCounter.findOneAndUpdate(
  { shop: shopId },
  { $inc: { seq: 1 } },
  { new: true, upsert: true, setDefaultsOnInsert: true },
);
const number = format(counter.seq); // default: INV-<slug>-<000000>
```

Rules:

- One allocation per invoice, never per request.
- Format is a pure function; changing it must not renumber existing invoices.
- Default format string: `INV-${shopSlug}-${String(seq).padStart(6, "0")}`
  (DECISION-1 covers statutory variants; the default is a placeholder, not a
  legal guarantee).
- Shop-scoped: two shops may both have `…-000001`.
- `upsert` + `$inc` is atomic in MongoDB; concurrency test required.
- The number is stored on the `Invoice` document and in the snapshot; it is
  never derived at read time.
- Sequence gaps are allowed (see §8.3). Duplicates are not.
- If DECISION-1 later specifies a financial-year reset, the counter key becomes
  `{ shop, period }` with a compound unique index — the format function is then
  the only code that changes.

## 10. Immutable invoice snapshot

### 10.1 What is stored

The snapshot is the full §1 contract plus:

```json
{
  "template": {
    "versionId": "…",
    "version": 2,
    "sha256": "…",
    "mappingHash": "…",
    "page": 0
  },
  "renderer": { "version": 1, "fontSha256": { "regular": "…", "medium": "…", "bold": "…" } },
  "eligibility": { "verificationSource": "razorpay_amount_verified", "checkedAt": "…" },
  "output": { "sha256": "…", "byteSize": 34211, "pageCount": 1 }
}
```

### 10.2 Immutability enforcement

- The `Invoice` model must prevent updates to the snapshot, number, order, shop,
  template reference and file keys. Options (choose one, document it):
  - a Mongoose `pre("findOneAndUpdate")`/`pre("save")` guard that throws for any
    modification of protected paths after creation;
  - explicit route-level policy: no update route exists, and all writes use
    `create()` only;
  - a schema-level frozen object (`Object.freeze` on the plain snapshot) plus the
    above guard.
- Recommended: **both** the guard and the create-only policy, with a unit test
  that attempts to mutate an issued invoice and asserts a failure.
- Reads must return stored values; never recompute display values for an issued
  invoice (a change to discount rules or shop name later must not alter a
  historical invoice's content).

### 10.3 Data retention

- Generated PDF bytes and the snapshot are both stored; the PDF is the artifact
  of record, the snapshot is the audit record.
- Replacing/removing a template touches neither.
- Deletion is out of scope (DECISION-8).

## 11. Refunds and adjustments

### 11.1 Adjusted before issuance (the common case)

`adjustOrderPaid` allows adjustments only in `paid`/`accepted`, i.e. **before**
completion, so by the time an invoice is issued the order already reflects them.

- Bill the payable `order.total` (= `updatedTotal`).
- Exclude removed lines.
- Include adjustment metadata: reason, timestamp, removed item names, refund
  amount, refund status.
- The discount is preserved across adjustment (`discountPercent` is retained),
  so `food - discount + parcel` reconciles against the updated total. Test an
  adjusted-order fixture.

### 11.2 Refund after issuance

Possible only through cancellation (which happens before completion today) or
future post-issue refunds.

- The issued invoice is **not** rewritten, renumbered, or reissued.
- If a refund/cancellation event occurs after issuance (for example an admin
  refund added later), the invoice record gains event metadata
  (`refundStatus`, `refundId`, `refundProcessedAt`) — but that is an **append-only
  event**, not a change to the invoice's rendered amounts.
- The snapshot's `payment.refundStatus` reflects state at issuance. Post-issue
  events must be recorded in a separate append-only field (for example
  `events: [{ type, at, amountPaise, reference }]`) so the original snapshot is
  untouched.
- The download is still available (the invoice happened) unless a human policy
  later says otherwise. Do not delete an invoice because of a refund.

### 11.3 Cancelled orders

- Never invoice `cancelled`, including cancelled-after-payment. The refund
  record is the financial artifact. The student still sees the existing default
  order bill with the cancelled status; no download action appears.
- If an invoice somehow exists for an order later found cancelled (data
  inconsistency), do not delete it and do not issue another; flag it in the
  final report and in a warning log.

## 12. Money formatting and amount in words

- Single formatter module inside `utils/invoice/`:
  - `formatPaise(paise)` → `₹1,23,456.78` (`en-IN` grouping, 2 decimals).
  - Negative amounts keep the minus sign (`−₹24.00`, U+2212 or ASCII `-`,
    choose one and use it everywhere).
- `amountInWords(paise)`:
  - Indian numbering: thousand, lakh, crore; paise as "and N Paise".
  - `23600` → `Two Hundred Thirty Six Rupees Only`.
  - `123456789` → `Twelve Crore Thirty Four Lakh Fifty Six Thousand Seven
    Hundred Eighty Nine Rupees Only`.
  - Zero paise omits the paise clause; non-zero adds `and <N> Paise`.
  - Deterministic, unit-tested against a fixture table (including 0.01, 0.99,
    1.00, 999.99, 1000.00, 100000.00, 10000000.00).
- Do not localize to other languages.
- `₹` must come from the formatter, so the glyph test in
  `04_PDF_TEMPLATE_ENGINE.md` §6.1 covers every money field.

## 13. Snapshot build order (deterministic)

```text
1. load order (lean) + shop (name, slug) + customer (name, phone, email)
2. eligibility checks (§7)
3. billable lines + money math (§6)
4. amount in words + display strings (§12)
5. template version + mapping hash (from the active version at this instant)
6. build plain object, deep-freeze
7. hash canonical JSON → snapshotHash
8. renderer → bytes → output sha256
9. allocate number (§9)
10. persist Invoice (unique order index)
```

Anything loaded after step 6 must not influence the snapshot. That includes the
shop document (load it before freezing and copy only `name`, `slug`, `_id`).

## 14. Tests this document implies

Minimum (full matrix in `07_TESTING_AND_ACCEPTANCE.md`):

1. Field mapping: every §2 row maps from the correct persisted field, proven by
   a fixture order with a variant, a discount, a parcel charge and a removed
   line.
2. `toPaise(order.total)` round-trip equals the original `totalPaise` for the
   fixture.
3. Reconciliation rejects a tampered total (mutated `order.total`) with
   `totals_mismatch` and produces no invoice.
4. Eligibility matrix: each status, each payment-evidence case, mock order
   marked `mock: true`, cancelled order ineligible.
5. Idempotency: parallel calls → one invoice, one number, one file.
6. Number uniqueness: 50 sequential invoices from one shop produce unique
   zero-padded numbers; two shops both start at `000001`.
7. Immutability: update attempt on an issued invoice throws.
8. Adjusted order: invoice bills updated total, excludes removed items, shows
   refund metadata.
9. History: replace + activate a new template, then download an older invoice —
   bytes and snapshot unchanged.
10. Amount in words fixture table.
11. `₹` formatting for all money fields (no `Rs.` fallback).
